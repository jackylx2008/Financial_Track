- 银行和支付宝/微信支付审核 HTML 的交易金额统一保留两位小数，并按每三位整数显示一个逗号，例如
  `24896.00` 显示为 `24,896.00`。
- HTML 数据新增独立的 `amount_display` 显示字段，页面交易金额列改为读取该字段；底层 `amount` 和
  `amount_value` 保持不变，不影响金额筛选、排序、退款匹配、退款净额汇总、流水哈希或归一化指纹。
- 已从现有归一化 JSONL 重建
  `processed_data/normalized/bank_transactions_full_review.html` 和
  `processed_data/normalized/payment_transactions_full_review.html`，没有重新扫描邮件或附件，也没有调用
  本地 AI/OCR。
- 实际页面数据验证：银行金额 `5215.41` 显示为 `5,215.41`，支付金额 `1400.00` 显示为
  `1,400.00`。
- 完整测试共 163 项通过，`compileall`、`flake8` 和 `git diff --check` 均通过。

## 大额资金流水上游追溯（开发分支）

- 新建 `feature/large-fund-trace-chain` 分支承载本轮功能，避免影响已经告一段落的主分支代码。
- 新增解释性资金池分配模型：在同一账户、同一币种内，将每笔支出分配到此前尚未耗用的收入；默认采用
  LIFO（最近收入优先），追溯窗口 365 天，大额阈值 10,000 元。
- 全部有效流水都参与资金池计算，小额支出会先消耗此前收入；HTML 主清单只展示达到阈值的大额转入、转出，
  避免因为忽略中间小额交易而高估可追溯金额。
- 默认只分析人民币借记/储蓄账户，排除信用卡、贷记卡、支付宝和微信支付账户；跨账户、跨币种和超过追溯
  窗口的流水不会互相匹配。账户尾号缺失时会显示明确提示。
- 新增 `large_fund_trace.json` 和交互式 `large_fund_trace_review.html`。页面按金额从大到小排序，支持方向、
  机构、币种、匹配状态和全文筛选；点击转出查看上游资金来源，点击转入查看后续去向及分配金额、间隔天数、
  推断置信度和原始来源定位。
- GUI 的“邮件数据归一化”页新增“打开大额资金追溯”按钮；银行归一化完成后自动生成追溯结果。已有
  `bank_transactions.jsonl` 也可通过 `python flows/large_fund_trace.py` 单独重建，无需重新扫描 PDF 或调用 AI。
- 页面醒目标明：资金具有可替代性，当前链条是可复核的分析模型，不是银行确认的资金因果关系；未匹配部分
  作为期初余额或窗口外资金显示。
- 使用当前本地 `bank_transactions.jsonl` 独立重建时未重新读取 PDF、未调用 AI/OCR，共生成 953 笔大额
  流水：其中大额转出 487 笔，476 笔完整匹配、9 笔部分匹配、2 笔未匹配。完整测试 169 项通过，
  `compileall`、`flake8` 和 `git diff --check` 均通过。
