# Financial Track 项目过程总结

## 项目目标

本项目用于个人消费订单和交易流水的本地化采集与整理，目标是在不接入平台私有接口、不抓包、不绕过平台风控的前提下，把多个安卓 App 中的可见信息沉淀为可继续处理的本地原始数据。

流水以安卓 App 截图及其结构化结果为主来源；邮件和网站 PDF 仅作为校验、对账和凭证材料。现有邮件/PDF 归一化能力为历史兼容实现，后续将从账本主输入调整为 reconciliation 输入。

当前阶段的重点是完成四个平台的原始数据获取：

- 京东：订单页面导出为 PDF。
- 淘宝：订单页面导出为 PDF。
- 拼多多：安卓订单页面截图，并通过外部 AI 服务识别整理为 JSON。
- 美团：安卓订单页面截图，并通过外部 AI 服务识别整理为 JSON。

截至当前阶段，四个平台的原始数据获取链路已经完成。京东、淘宝以 PDF 作为原始数据归档形式；拼多多、美团以截图作为视觉输入，并已通过外部 AI 服务生成结构化 JSON。

## 总体技术路线

项目采用“平台采集入口 + 基础能力模块 + 本地数据产物”的方式推进。

京东和淘宝等 Web 页面仍可打印归档为 PDF，但 PDF 的定位是复核和对账，不作为流水主来源。

移动端交易数据来自安卓 App 页面。项目通过 ADB 获取 USB 实体手机截图并连续滚动交易流水列表；已有订单类截图仍可使用支持视觉输入的 llama.cpp OpenAI 兼容服务整理为 JSON。

所有真实采集数据、日志、浏览器登录状态和环境变量都保存在本机，不提交到版本库。

## 阶段一：项目基础结构

项目先搭建了基本工程结构：

- 根目录仅保留 `main.py` 主图形入口、`pdf_ocr_review_app.py` 独立只读 PDF/OCR 审核入口和
  `logging_config.py` 日志配置。
- `flows/*.py` 承接独立工作流，例如 `flows/jd_pdf_bot.py`、`flows/financial_email_bot.py`。
- `flows/android_transaction_capture.py` 是统一安卓交易流水采集入口。
- `flows/modules/android_adb.py` 封装设备发现、授权检查、屏幕尺寸、截图、坐标换算和滑动。
- `flows/modules/android_macos.py` 与 `flows/modules/android_windows.py` 分别初始化两种桌面系统的 ADB。
- `flows/modules/` 放置财务领域、配置、JSON 解析和外部服务客户端等可复用模块。
- `flows/workflows/` 放置围绕具体任务的流程编排。
- `config.yaml` 和 `common.env` 分离通用配置与本机私有配置。
- `raw_data/` 和 `logs/` 作为本地运行产物目录，并通过 `.gitignore` 排除。

这个结构保证了后续新增平台或新增处理流程时，可以优先复用已有的配置、日志、外部 AI 客户端和文件输出逻辑。

## 阶段二：京东 PDF 获取

京东链路由 `flows/jd_pdf_bot.py` 实现。

实现方式：

- 使用 Playwright 启动 Chromium 持久化上下文。
- 浏览器用户数据目录保存在 `raw_data/jd_browser_profile`，用于复用登录状态。
- 根据 `config.yaml` 中的 `flows.jd_pdf.order_pages` 配置生成年份和页码任务。
- 访问京东订单列表 URL，等待页面加载和必要的手工登录。
- 使用 Playwright 的 `page.pdf()` 直接渲染 A4 PDF。
- PDF 文件按年份、页码和时间戳命名，输出到环境变量配置的目录。

这一阶段解决了京东订单页面批量归档的问题，避免依赖系统打印对话框，也减少了鼠标键盘自动化的不确定性。

## 阶段三：淘宝 PDF 获取

淘宝链路由 `flows/taobao_pdf_bot.py` 实现。

实现方式：

- 使用 `pyautogui` 操作已经打开的浏览器订单页。
- 启动后预留倒计时，人工把鼠标放到“下一页”按钮位置。
- 每轮点击下一页，等待页面加载。
- 触发 `Ctrl+P` 打开浏览器打印流程。
- 依赖浏览器默认打印目标为“另存为 PDF”。
- 自动输入按日期和页码生成的 PDF 文件名。
- 循环执行，直到用户按 `Ctrl+C` 或触发 pyautogui 安全停止。

这一阶段使用的是半自动方案，原因是淘宝页面和浏览器打印行为对登录状态、弹窗、页面布局更敏感。该方案保留了人工可控性，同时减少了重复翻页和保存文件的机械操作。

## 阶段四：安卓 App 交易流水截图获取

所有安卓 App 共用 `flows/android_transaction_capture.py` 入口，GUI 中统一放在“安卓 App 采集”页签。

实现方式：

- 通过 ADB `exec-out screencap -p` 获取当前安卓屏幕截图。
- 只连接 USB 实体手机，不探测或适配 MuMu 等模拟器。
- macOS 从显式路径或 `PATH` 查找 ADB；Windows 还会检查 Android SDK 环境变量和标准目录。
- App 名称、输出目录、参考分辨率和默认滑动参数由本机 `common.env` 配置。
- 自动发现设备、检查授权并读取屏幕尺寸，再把参考滑动坐标换算到实际分辨率。
- 支持三种采集方式：
  - `capture`：截取当前屏幕。
  - `capture-scroll`：按固定页数截图并滑动。
  - `capture-until-end`：截图、滑动并通过相邻截图相似度判断是否到达列表底部。
- 不同 App 可配置不同滑动距离，保留适量截图重叠，降低金额或关键字段被滑过的风险。
- 遇到“显示更多”等需要人工干预的页面时，可以人工处理后继续。

截图目录完全由本机 App 配置决定。这一阶段完成了移动端交易流水页面的通用批量视觉原始数据采集。

## 阶段五：外部 AI 识别与 JSON 整理

拼多多和美团截图识别链路由 `flows/order_image_ai.py` 和 `flows/workflows/order_image_extract.py` 实现。

实现方式：

- 入口脚本根据平台解析默认截图目录。
- 支持识别最新一张截图，也支持 `--all` 批量识别目录内所有 PNG。
- AI 客户端读取 `config.yaml` 中的 `llamacpp` 连接配置。
- AI 服务由其他运行时项目负责启动和管理，本项目只检查并调用现有服务。
- 调用 OpenAI 兼容的 `/chat/completions` 接口，并以 data URL 方式传入图片。
- 提示词要求模型只输出 JSON，不输出 Markdown 或解释。
- JSON 解析模块会兼容模型输出中可能出现的代码块或额外文本。
- 每张截图单独保存一个 JSON 文件。
- 识别进度和结果摘要写入 `logs/order_image_ai.log`。

默认 JSON 产物保存在：

- `raw_data/order_json/pdd/`
- `raw_data/order_json/meituan/`

当前 JSON 顶层结构包括：

- `platform`
- `source_image`
- `orders`
- `warnings`

每条订单记录包括商家、状态、标题、规格、数量、实付金额、原价、运费、下单时间、订单号、物流、可见操作按钮、是否截断、置信度和备注等字段。

## 阶段六：银行 PDF 表格缓存与 HTML 审核

银行流水 PDF 可通过 GUI“PDF 转 HTML 审核”页签或 `flows/pdf_to_html.py` 单独预处理。

- 默认扫描 `raw_data/bank/**/*.pdf`，不修改原始文件。
- 保存 PDF 完整 SHA-256、页码、页面尺寸、表格边界、列宽以及原始行列内容。
- 以 SHA-256 命名缓存；再次处理同一文件时复用缓存，不重复逐页扫描。
- `pdf_hash_index.json` 持久记录每个哈希的来源路径、提取状态、文本缓存状态及 OCR 核验状态；改名不导致重复识别。
- 汇总生成 `processed_data/pdf_html_review/bank_pdf_tables_review.html`，可按机构、PDF 和页码切换。
- HTML 保持原表格的行列顺序和列宽比例，并提供调用本机默认程序打开原 PDF 的入口。
- 未识别到稳定表格的页面保留明确提示，避免把无结果误认为空账单。
- `flows/pdf_html_ocr_compare.py` 对缓存矩阵与 HTML 做全量严格等值检查，并对每份 PDF 的首、中、末页
  分别渲染原表格和 HTML 表格进行独立 OCR 对比；默认仅处理新哈希，低分辨率边缘页自动提高到 300 DPI 复核。
- 后续归一化对已缓存哈希读取审核阶段保存的原始解析文本，不再打开 PDF；新哈希完成提取和核验后自动进入同一链路。

缓存和 HTML 均包含个人财务信息，只保存在被 Git 忽略的 `processed_data/` 中。

## 阶段七：流水哈希与支付链路

- 每个原始来源记录使用完整 `source_record_sha256` 标记；每条归一化流水和财务事实使用唯一
  `flow_hash_sha256` 标记，短 ID 仅作兼容索引。
- 银行流水汇总到一个审核 HTML；支付宝和微信汇总到另一个支付审核 HTML。
- 工商银行信用卡存在重复邮件/PDF 组时，从 GUI“邮件获取账单”页打开来源选择审核页；人工确认的一组
  作为权威来源，未选组在下次银行归一化解析前排除。选择记录只保存在 Git 忽略的 `raw_data`。
- 订单、支付宝/微信、银行卡各自保持独立流水，不因关联而合并为一条记录。
- `payment_chain_links.jsonl/json` 以带 SHA-256 的关系边连接“订单 → 支付方式 → 银行资金来源”。
- 只有确定性较强的关系标为 `linked`；多候选或证据不足的关系标为 `candidate`，留待人工审核。

## 已形成的关键经验

1. 流水主数据优先来自移动端 App 截图。ADB 截图不需要修改 App，也不需要接入平台内部接口。
2. 邮件和 Web 平台 PDF 保留为可复核凭证，只用于校验、对账和差异追踪。
3. 连续截图必须保留一定重叠。订单卡片高度不固定，滑动距离过大容易漏掉金额、状态或订单标题。
4. 到底判断不能只依赖固定页数。通过截图相似度判断可以减少无效截图，同时保留手工继续的入口。
5. AI 输出必须有强约束。提示词、JSON 提取、warnings 字段和 raw output fallback 是保证批量处理可追踪的关键。
6. 真实路径和隐私数据必须和代码隔离。`common.env`、`raw_data/`、`logs/` 和浏览器 profile 都不应进入版本库。

## 当前限制

当前阶段仍有一些边界需要后续处理：

- 淘宝 PDF 目前尚未统一解析为订单级 JSON；京东 PDF 已完成订单级归一化。
- 拼多多和美团截图识别依赖视觉模型能力，金额、订单号、截断订单仍需要抽样复核。
- 连续截图会产生重叠订单，后续需要订单级去重和跨截图合并。
- 不同平台字段命名和可见信息不完全一致，后续需要统一订单 schema。
- AI 识别依赖外部服务可用性和所选视觉模型能力，服务生命周期由专用运行时项目维护。

## 下一阶段建议

后续可以按下面顺序推进：

1. 建立安卓银行流水截图 JSON schema，并先实现光大银行识别。
2. 实现跨截图交易去重，以安卓截图结构化结果生成权威流水中间层。
3. 将邮件/PDF 解析结果改为 reconciliation 输入，生成缺失、金额不符和日期不符等差异报告。
4. 增加字段校验和人工复核清单，集中处理低置信度与截断记录。
5. 将安卓流水与订单明细关联后进入账本、分类、统计和 Excel 输出流程。

## 阶段结论

本阶段已经完成多平台原始订单数据获取的核心闭环。京东和淘宝完成 PDF 归档；拼多多和美团完成截图采集，并已经通过外部 AI 服务转换为 JSON。项目现在具备继续推进“订单级清洗、去重、统一 schema、分类统计和报表输出”的基础。
